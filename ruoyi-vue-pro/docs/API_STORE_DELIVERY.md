# 团团园园杂货铺：配送、自提与见面付款接口

当前服务器开发环境 `https://mall.nexrur.ai`，同一 Java 后端；已补齐自提见面付款、普通见面订单完成前取消及店主线下退款登记流程。

## 顾客端约定

结算 `GET /app-api/trade/order/settlement`、创建 `POST /app-api/trade/order/create`：

- `deliveryType`：1 快递（原逻辑）、2 自提、3 店铺自己送。当前六款商品均支持 `[2,3]`。
- `paymentMethod`：1 在线付款、2 见面付款；不传或 null 默认在线付款。
- 店铺自己送免费，校验收件地址归属；复用支持快递商品的可配送能力，也允许商品显式配置方式 3。纯自提商品不能转为配送。尚无地域限制、起送金额配置，不以此声称已完成配送范围验收。
- 见面付款支持普通店铺配送、自提，不支持快递代收和营销活动订单。
- 见面付款创建后 `status=10`、`payStatus=false`、`payOrderId=null`。配送订单待配送，自提订单待收款；不得因 status=10 就当成已付款。依据 `paymentMethod` 和 `payStatus` 显示付款状态，不拉起在线支付。
- 在线支付保持旧逻辑，使用返回的支付单拉起支付。
- 已存在订单默认 paymentMethod=1，不转换原订单或改其金额。

详情与列表提供 paymentMethod、payStatus；详情另提供 receiptMethod、receiptAmount（分）、receiptTime；顾客端不返回收款管理员 ID。普通见面付款配送、自提订单在实际状态 10、20 时均允许本人取消，包括已经登记收款及配送中的订单。见面付款的交货完成只由 Admin 确认，未收款不能完成，顾客确认收货及超时自动收货不能绕过该约束。

### 服务端分组与计数（兼容 2026-11-17 约定）

付款与交货分别判断，同一订单可以同时进入两个分组。沿用现有请求参数和计数字段：

| 服务端分组 | `/app-api/trade/order/page` 参数 | `/get-count` 字段 | 查询条件 |
| --- | --- | --- | --- |
| 全部订单 | 不传 status | allCount | 当前用户全部未删除订单，不重复计数 |
| 待付款 | status=0 | unpaidCount | payStatus=false 且实际 status 为 0、10 或 20 |
| 待发货／待取货 | status=10 | undeliveredCount | 实际 status=10，包含已付款和未付款 |
| 待收货 | status=20 | deliveredCount | 实际 status=20，包含已付款和未付款 |

店铺配送、见面付款的新订单实际为 status=10、payStatus=false，同时进入待付款和待发货；开始配送后实际为 status=20、payStatus=false，同时进入待付款和待收货；登记收款后只退出待付款，仍待收货，确认送达后为30。自提未收款订单同时进入待付款和待取货，收款后仍为10待取货。历史已付款但未配送的订单保留真实状态和付款记录，不因新规则回写。已完成、取消订单不进入待付款，即使有历史异常未付款标记。

分组计数与分页列表使用同一查询条件，保留当前用户、逻辑删除及现有租户隔离。各分组数量允许重叠，不能相加作为全部订单数量。返回的 status 保留原履约值，列表新增 payStatus；不得把待付款分组中的见面付款订单当成在线支付订单或据此创建微信支付单。此次只改变查询，未修改真实订单、付款、金额及配送状态。

已通过 6 项 H2 实际查询与响应映射测试及此前 33 项收款、自提、在线支付回归，并打包重启开发后端。本地和公网只读接口验证账号 298 的待付款、待发货均为 2，订单 284、286 同时存在于两个列表；原状态、付款与金额未变。记录为 `_local/serverdev/order-groups-live-verification.json`。未在本机构建或上传顾客小程序，生产 JAR 未修改。

### 完成前取消与顾客端三分组（2026-11-19）

本轮顾客端交接采用“全部｜配送/自提｜取消/完成”，服务端参数和计数字段保持兼容：全部不传 status；配送/自提由前台按 ID 倒序归并状态 10、20 的独立分页；取消/完成归并状态 30、40，查看的是业务订单，不是售后服务单。履约角标仅合并互斥的 undeliveredCount、deliveredCount，不加 unpaidCount，也不将售后或未评价数量当作结束订单数量。

取消继续调用 `DELETE /app-api/trade/order/cancel?id=...`，成功响应仍为 `{ "code": 0, "data": true }`：

- 普通见面付款订单（type=0、deliveryType=2/3、paymentMethod=2、refundStatus=0）在状态 10、20 时均可由本人取消，不以是否收款为限制；保留未付款状态 0 的兼容处理。
- 在当前租户中先校验归属，再锁定订单并重新核对归属、状态；已完成 30、已取消 40、未知状态均拒绝，不重复返库存或记取消日志。
- 取消与收款、开始配送、确认送达、确认取货使用同一订单行锁。与完成竞争时仅一个终态成功：先完成则取消拒绝，先取消则完成拒绝。先收款后取消则原收款记录保留；先取消则后续收款拒绝。
- 取消仅将业务状态改为 40 并记录取消类型和时间。payStatus、payTime、payChannelCode、payOrderId、线下收款方式/金额/管理员/时间及原退款记录不清空、不伪造。既有库存、优惠券、积分/成长值等取消后置处理在事务中执行一次，失败回滚。见面付款取消不关闭关联在线支付单，也不调用在线退款。
- 历史在线订单仍仅允许未付款时直接取消；在线已付款或支付网关已成功但回调延迟的订单拒绝直接取消，不借此绕过真实退款流程。
- 见面订单完成由 Admin 控制：配送先开始，再登记收款并确认送达；自提先登记收款再确认取货。顾客收货接口和自动收货任务不能完成见面付款订单，通用收货核心也拒绝未付款订单。

取消成功不等于退款成功。已经收到的钱由店主核实并线下退回，再使用下述 2026-11-20 新增的登记接口；不伪造微信退款或未收款状态。顾客端再次展示页面时重新读取详情、分页和计数；接口失败、响应丢失时先刷新核实结果，不本地伪造取消，不自动重复写入。

## 管理端

- `PUT /admin-api/trade/order/store-delivery?id=...`，权限 `trade:order:update`：开始自送，status 10→20；见面付款允许未收款发出，在线支付必须已付款。
- `PUT /admin-api/trade/order/confirm-offline-payment`，独立权限 `trade:order:confirm-offline-payment`，JSON `{ "id": 订单ID, "amount": 应收分值, "method": "cash或scan" }`。
- 收款只接受普通见面付款、未登记付款、未退款、无在线支付单的订单。**店铺配送仅允许已开始配送的状态20，状态10提前收款由后端拒绝；自提只允许状态10。** 金额必须与 payPrice 精确相等且大于 0，方式仅 cash / scan。管理员在线下收到钱后点击“已付款”进行人工登记，记录管理员 ID、时间、实收方式和金额。履约状态不变，店铺配送仍为20、自提仍为10；payStatus=true，payChannelCode 为 offline_cash/offline_scan，不创建或修改微信支付单。
- `PUT /admin-api/trade/order/store-receive?id=...`，权限 `trade:order:update`：已收款且配送中才能确认送达，status 20→30。
- 自提使用原 `PUT /admin-api/trade/order/pick-up-by-id?id=...` 或 `/pick-up-by-verify-code?pickUpVerifyCode=...`，权限 `trade:order:pick-up`，不走店铺配送接口。界面称“确认已取货”：校验当前租户、行锁中的最新订单状态、已付款及门店绑定账号后，将状态从 10 改为 30 并记录取货时间；见面付款订单退款状态须为 0。未收款、未绑定、重复取货或不存在的订单拒绝。正式门店已绑定现有 admin。
- 操作持有当前租户订单行锁，重复收款拒绝；支付后置处理在收款事务内只执行一次。订单调价入口拒绝见面付款订单，防止与收款并发改变金额。
- 店主 Admin 对店铺配送订单，主标签随实际进度显示“待配送 / 配送中 / 已完成 / 已取消”，付款结果单独展示。状态10只显示“开始配送”和备注，20未收款只显示“已付款”和备注，20已收款只显示“确认送达”和备注，30只保留适用的备注操作。付款与交货分别记录不代表可跳步骤。
- 见面收款不接在线退款接口，售后申请明确提示联系店主核实线下退款。店主实际退钱后使用下述独立登记流程，不创建支付渠道退款单。

### 已取消订单的线下退款登记（2026-11-20）

Admin 列表沿用现有布局：主标签为“已取消”，下方付款信息分别显示“未付款”“已付款 · 待退款”“已退款”。列表不增加退款按钮；订单详情的“确认已退款”在左、备注在右。弹窗金额固定为订单全额，选择现金退回或微信转回，勾选已实际退回，再二次确认。按钮只登记，不自动转钱；接口失败或响应丢失时重新查询，不自动重复提交。

`PUT /admin-api/trade/order/confirm-offline-refund`，独立权限 `trade:order:confirm-offline-refund`：

```json
{ "id": 1900000010, "amount": 1500, "method": "cash" }
```

- 仅普通见面付款、自提或店铺配送、已取消 40、已收款的订单可以登记；必须无在线支付单、无既有部分/全部退款、无既有线下退款登记。金额须等于 payPrice 且大于 0，方式只接受 cash/scan。首版仅支持全额退款。
- 服务端在当前租户订单行锁中重新校验，写入 `offlineRefundMethod`、`offlineRefundAmount`、`offlineRefundOperatorId`、`offlineRefundTime`，同时把实际退款汇总 `refundStatus=20`、`refundPrice=payPrice` 更新为全额已退。订单始终为 40；原 payStatus、payTime、收款方式/金额/时间/操作人全部保留，不把原付款改成未付款。
- 退款登记与操作日志在同一事务中写入；日志失败回滚，重复或并发登记只允许一次。库存、营销已在取消时处理，登记退款不再次退库存、处理积分或创建售后单，不调用微信/钱包退款 API。
- Admin 分页及详情返回四个新登记字段；顾客 `/app-api/trade/order/page` 与 `/get-detail` 返回方式、金额、时间和退款汇总，**不返回退款管理员 ID**。顾客端只读取，不提供登记接口；顾客页面是否显示新退款信息由其独立前端对接，不以本轮 Admin 修改声称顾客小程序已更新。
- 已收款取消即为待退款，不自动写退款时间或确认退款。保留既有异常或部分退款记录，这类订单不提供本按钮，需店主单独核对。

## 微信设置

物流与收款设置页面保留，当前首页入口按用户要求隐藏；不展示通用支付应用列表。

微信收款按当前租户应用标识 mall 查找应用与 wx_lite 渠道，不写死应用编号。实际商户配置仍在原支付渠道界面维护。当前开发库商城应用没有微信小程序支付渠道记录，不能声称已经可以实扣款。

微信物流设置：`GET/PUT /admin-api/trade/delivery/wechat/config`，使用运费模板查询/更新权限；仅保存寄件人、联系电话、寄件省市区及详细地址、快递代码 deliveryId、合作账号 bizId、服务类型 serviceType，按租户隔离。`GET /admin-api/trade/delivery/wechat/accounts` 使用已有顾客小程序客户端调用微信物流助手，返回安全字段的绑定账号列表；失败不透传 Token 或请求内容。

微信 AppID/AppSecret 沿用已有小程序配置；商户密钥与证书仍在原支付渠道配置，不进入源码。物流设置保存、账号同步不等于实际生成运单；自动生成电子面单、真实快递下单与取消接口仍需后续实现及真实账号联调，当前订单仍可用原手填快递单号发货。
